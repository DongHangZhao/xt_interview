## Q1：启动报 `Port 7218 was already in use`，但我明明配置的 8080

**现象**
```
Web server failed to start. Port 7218 was already in use.
```
可配置文件里明明白白写的是 `server.port=8080`。

**排查过程**
1. 确认配置文件没写错 → 没错
2. 全局搜项目里有没有 7218 → 没有
3. 检查系统环境变量（机器级、用户级）→ 都没有
4. 打印 shell 环境变量 → 找到了：
   ```
   SERVER__PORT=7218
   SERVER__HOST=127.0.0.1
   ```

**原因**

IDE（CodeBuddy / IntelliJ 等）为了给自身后端服务用，会向子进程注入一批环境变量，
其中 `SERVER__PORT=7218` 被 Spring Boot 的**宽松绑定规则**自动映射成了 `server.port`：

```
SERVER__PORT  →  server.port
```

宽松绑定优先级：**命令行参数 > 环境变量 > 配置文件**。所以配置文件里的 8080 被覆盖成了 7218。

**解法**

不改系统环境变量（那样会影响 IDE 自己），在启动命令中显式指定：

```bash
mvn spring-boot:run -Dspring-boot.run.arguments="--server.port=8080"
```

命令行参数优先级最高，可覆盖环境变量。

**通用性**：在 IDE 里跑任何 Spring Boot 项目都可能遇到，值得记住。

## Q2：删除部门后重新创建同名同编码，返回 500

**现象**
```
POST /api/departments  →  HTTP 500 Internal Server Error
```

后端日志：
```
DataIntegrityViolationException:
Duplicate entry 'test' for key 'uk_department_code'
```

**原因**

唯一索引作用在**物理行**上。软删除只是标记 `deleted=1`，行仍在表里，索引依然占着 `test` 这个值。

而我最初的唯一性校验写的是：
```java
existsByCodeAndDeleted(code, 0)   // 只查未删除的记录
```

于是产生了矛盾：
```
校验层：查 deleted=0 → 查不到 → 校验通过
数据库：查全表 → 发现 test 还在 → 插入失败
```

**解法（分两步）**

第一步，快速止血：给 `DataIntegrityViolationException` 加全局处理器，
把数据库异常翻译成友好提示，避免用户看到 500。

第二步，根治：把唯一性校验口径改为与数据库约束一致。

**关于"要不要去库里物理删除"**

不可以。物理删除会丢失审计记录，等于放弃软删除的意义。

**最终方案**：
1. 唯一索引降级为普通索引，唯一性交给应用层
2. 软删除时把唯一码改写为 `原码__del_时间戳`

```
删除前: test
删除后: test__del_1789012345678    ← 行还在（deleted=1），但 test 空出来了
重建:   用 test → 成功
```

用毫秒时间戳而非固定后缀（如 `__del`），避免反复删除同名记录时二次冲突。

## Q3：管理员能创建同级管理员，却不能修改同级，逻辑不一致

**现象**

测试权限时发现两个矛盾的行为：
```
管理员创建 roleLevel=2 的账号 → 成功（HTTP 200）
管理员修改另一个 roleLevel=2 的账号 → 403
```

**分析**

第一版校验写的是 `target > operator.getRoleLevel()`，即"目标权限严格大于自己"才拦截。
按这个规则，管理员（2）创建同级（2）是允许的。

但创建同级管理员本身就是一条**提权路径**：
```
攻击者（管理员A）创建管理员B
  → A 和 B 互相配合，把管理员C提升为超管
  → A 或 B 获得超管权限
```

这就是典型的**横向提权**。

**解法**

统一为 `target >= operator.getRoleLevel()`（小于才拦截），超管单独放行：

```java
if (operator.isSuperAdmin()) return;   // 超管不受限
if (target >= operator.getRoleLevel()) throw new BusinessException(...);
```

为什么超管要放行？因为否则系统将无法通过界面新增超管，只能改数据库，
这是不合理的。超管之间互相管理是设计意图。

## Q4：编译报错"找不到 findAll(Specification, Pageable)"

**现象**
```
ERROR: 找不到方法 findAll(Specification<Account>, Pageable)
  候选方法: findAll(Example<S>, Pageable) 等
```

**原因**

Spring Data JPA 4（Spring Boot 4 起）调整了接口设计，
`Specification` 相关的查询方法**不再混入 `JpaRepository`**，
被拆分到独立的 `JpaSpecificationExecutor` 接口。

```java
// Boot 3.x：直接继承 JpaRepository 即可
public interface AccountRepository extends JpaRepository<Account, Long> {}

// Boot 4.x：必须显式继承 JpaSpecificationExecutor
public interface AccountRepository
    extends JpaRepository<Account, Long>, JpaSpecificationExecutor<Account> {}
```

**说明**：这是 Spring Boot 4 的新变化，社区上 Boot 2.x/3.x 的资料都不适用。
面试时如果问到 Boot 4 的兼容性变化，这是一个有价值的实例。

## Q5：Flyway 脚本改完后，启动永远失败

**现象**
```
Caused by: Schema `xt_interview` contains a failed migration to version 5 !
```

我第一次执行 V5 脚本失败（原因见 Q6），修好脚本后重新启动，
**报错依然一样，脚本根本没重新执行**。

**原因**

Flyway 在 `flyway_schema_history` 表里记录了 `success = 0` 的失败标记。
只要这张表里存在失败记录，Flyway 就拒绝启动，且**不会重跑**该脚本。

**解法**

清掉失败标记：
```sql
DELETE FROM flyway_schema_history WHERE success = 0;
```

或者用 Flyway 官方命令（需先给 maven 插件配置数据库连接）：
```bash
mvn flyway:repair
```

**根本教训（更重要的）**

Flyway 已执行成功的迁移脚本**不允许再修改**，因为 Flyway 用 checksum 校验文件是否被改动过。

正确做法：修改已执行的脚本必须**新建编号更大的脚本**，如 V4 → 改完后叫 V6。
本次 V4（唯一索引降级）是新建的脚本，没有修改已有脚本，因此未触发此问题。

## Q6：Flyway 报 `Error Code: 1452` 外键约束失败

**现象**
```
Cannot add or update a child row: a foreign key constraint fails
("xt_interview"."sys_account", CONSTRAINT "fk_account_department" ...)
```

**原因**

V5 脚本里我给账号写死了部门 ID：

```sql
INSERT INTO sys_account (..., department_id, ...) VALUES
('emp_dev01', ..., 3, 0),     -- 假设部门ID=3是研发部
```

但因为之前手动测试时创建过临时部门，**部门自增 ID 已经漂移**，
ID=3 实际不存在（或不是研发部），外键校验失败。

**解法**

改用子查询按业务编码关联，不依赖任何具体 ID：

```sql
INSERT INTO sys_account (..., department_id, ...) VALUES
('emp_dev01', ..., (SELECT id FROM sys_department WHERE code = 'IT_DEV'), 0);
```

**通用原则**：迁移脚本中**永远不要硬编码自增主键**。
用业务唯一编码（如 `code='IT_DEV'`）做关联锚点，脚本在任何库上都能执行。

## Q7：`vue-tsc` 报 `TS2740: AxiosResponse 赋给 any[]`

**现象**
```
src/views/UserManagement.vue(159,5): error TS2740:
Type 'AxiosResponse<any, any, {}, any>' is missing the following
properties from type 'any[]': length, pop, push, concat, and 28 more.
```

**原因**

`request.ts` 的响应拦截器把 `AxiosResponse` 外壳剥掉了：
```ts
request.interceptors.response.use((response) => {
  return response.data      // 运行时确实只剩 data
})
```

但 **axios 的 TypeScript 类型定义不知道你在拦截器里做了手脚**，
调用方拿到的返回值仍被标注为 `AxiosResponse<T>`。

这是典型的「运行时行为与类型声明不一致」。

**解法**

在 `request.ts` 导出泛型化的封装函数，重新声明返回类型：

```ts
export function get<T = any>(url: string, config?: AxiosRequestConfig): Promise<T> {
  return request.get(url, config) as unknown as Promise<T>
}
```

api 层就能写 `get<Department[]>('/departments')`，类型一路穿透到组件。

## Q8：`delete data.password` 报 TS2790

**现象**
```
error TS2790: The operand of a 'delete' operator must be optional.
```

**原因**

`{ ...formData }` 推导出的类型中 `password` 是**必填属性**，
TypeScript 不允许 delete 必填属性。

**解法**

显式声明为宽松类型：
```ts
const data: Record<string, any> = { ...formData }
delete data.password
```

## Q9：分页页码错乱，翻页后数据不对

**现象**

第一页显示正常，点第二页后数据重复或跳号。

**原因**

需求要求后端 `page` 从 **0** 开始，但 Element Plus `el-pagination` 从 **1** 开始。

第一版写的是：
```vue
v-model:current-page="query.page"
```

`v-model` 是双向绑定，组件把 1-based 的值写回了 0-based 的变量，
导致 `query.page` 被污染。

**解法**

改用单向绑定，转换只在展示和事件处理两处发生：

```vue
:current-page="query.page + 1"          <!-- 传给组件：0-based → 1-based -->
@current-change="handlePageChange"      <!-- 组件回传 1-based -->
```
```ts
function handlePageChange(val: number) {
  query.page = val - 1                  // 1-based → 0-based
  loadUsers()
}
```

## Q10：Vite 端口自动从 5173 变成 5174

**现象**

执行 `npm run dev` 后，日志显示的是 5174，不是配置里的 5173。

**排查**
```bash
netstat -ano | grep ":517[34]"
```
```
TCP    [::1]:5173   LISTENING   41536    ← 旧进程还占着
TCP    [::1]:5174   LISTENING   39444    ← 新进程只能换端口
```

**原因**：5173 被之前的 Vite 进程占用。

**关键点**：Vite 端口被占时会**静默 +1，不打印任何警告**，
很容易误判成"配置生效了"。

**解法**
```bash
netstat -ano | findstr :5173
taskkill /PID 上面的PID /F
```
然后重新 `npm run dev`。

## Q11：部门名称重复 / 编码复用相关问题

这一组是用户实测提出的，单独记录。

**Q11.1：为什么可以创建多个同名部门？**

骨架只在 `code` 上建了唯一索引，`name` 没有约束。业务上「研发部」出现两次说不通。
→ 增加 `existsByNameAndDeleted` 应用层校验，前端同步加预校验。

**Q11.2：禁用状态的部门，用户照样能选？**

骨架中 `status` 字段只影响列表上的标签展示，没有任何逻辑阻止分配用户。
→ Service 层增加校验，禁用部门拒绝**新分配**，
但**已分配用户保持不动**（否则部门一禁用，手下员工部门信息全空）。

实现细节：更新场景传入原部门 ID，若目标部门 == 原部门则放行，
否则部门一旦被禁用，其下所有用户连改手机号都保存不了。

```java
boolean stayingInSameDepartment = departmentId.equals(originalDeptId);
if (disabled && !stayingInSameDepartment) throw ...;
```

**Q11.3：删除后的编码还在库里，要手动去删吗？**

不要。详见 Q2。
正确做法是软删除时改写唯一码（`test__del_时间戳`），
既能保留审计记录，又立即释放原编码。

## Q12：用户在 Git Bash 里 curl 传中文参数返回非 JSON

**现象**
```bash
curl "http://localhost:8080/api/accounts/page?username=分页甲"
# 返回空或非 JSON 内容
```

**原因**：Git Bash 的参数编码问题，URL 里的中文没被正确 URL 编码。

# 下篇：预判的面试官提问

## 关于需求理解

**Q：为什么选软删除而不是物理删除？**

软删除保留了被删数据，可审计、可追溯、可恢复。
企业级系统通常不允许物理删除用户和部门这类主数据。
代价是需要处理唯一索引冲突（见 Q2 的处理方式）。

**Q：部门删除时用了 `ON DELETE SET NULL`，为什么不是 CASCADE？**

`CASCADE` 会在物理删除部门时连带删除其下用户，这不可接受。
`RESTRICT` 则会阻止删除，导致部门永远删不掉。
`SET NULL` 让用户变成"未分配部门"，与需求中"部门为可选字段"的定位一致。

虽然当前是软删除、外键实际不会触发，但约束定义要为将来的物理删除/数据清理留出正确语义。

---

## 关于权限设计

**Q：为什么不用 Spring Security 的 @PreAuthorize，而是自己写 PermissionChecker？**

两者都用了，但分工不同：
- `SecurityConfig` 放行所有请求，保留基础设施与 `@EnableMethodSecurity`
- 实际鉴权由 `JwtAuthenticationFilter` → `UserContext` → `PermissionChecker` 完成

原因是项目已有一套完整的 JWT 认证链路，如果再让 Spring Security 接管，
会出现两层过滤器同时鉴权，规则重复且排查困难。

选自建方案还有一个原因：`PermissionChecker` 承载的是**业务规则**而非路径规则，
比如"不能操作权限不低于自己的账号""不能停用自己"，这类规则用注解表达反而不直观。

**Q：JWT 里已经有 roleLevel 了，为什么还要回数据库查？**

因为 JWT 签发后到过期（24 小时）之间，权限可能已被管理员调整，或者账号被禁用/删除。
如果直接信 token 里的旧 `roleLevel`，**权限下调后旧 token 仍持有高权限**。

每次请求做一次主键索引查询的成本，换取权限实时准确，这个权衡是值得的。
高并发场景可以改为 Redis 缓存权限变更，或缩短 JWT 有效期 + 引入刷新令牌。

**Q：ThreadLocal 忘记清理会怎样？**

Tomcat 使用线程池复用线程。若不清理，
下一个请求处理时 `UserContext.get()` 可能拿到**上一个用户的权限对象**。

我实测过：如果不写 `finally { UserContext.clear(); }`，
在测试中先用一个管理员账号发请求、再用普通账号发请求，
第二个请求有机会继承管理员权限。这是隐蔽且严重的越权风险。

**Q：怎么防止普通用户给自己提权？**

三层防护：

1. **接口层**：`/my-profile` 使用字段白名单，
   完全不读取 `roleLevel / isSuper / status / departmentId`。
   前端恶意提交这些字段也不会落库。
2. **身份识别**：接口不接收 id 参数，后端从 token 识别当前用户，
   物理上无法修改他人。
3. **管理端校验**：`checkCreateAccount` 要求目标权限严格低于自己。

实测：普通用户提交 `roleLevel: 3`，接口返回 200 但库中仍是 1。

**Q：前端隐藏菜单算不算安全控制？**

不算。**安全边界必须在后端**。

前端隐藏菜单（`v-if="isAdmin"`）和路由守卫只是体验优化，
用户通过浏览器控制台或直接调用接口仍能触达。
真正的防线是后端的 `PermissionChecker`，我在交付文档和代码注释中都标注了这一点。

## 关于数据库

**Q：唯一索引和软删除冲突怎么解决？为什么不用 `UNIQUE(code, deleted)`？**

`UNIQUE(code, deleted)` 看似可行，实则有个坑：
删掉一条 `code='test'` 的记录（变为 `(test, 1)`），
再删掉另一条 `code='test'` 的记录（也是 `(test, 1)`）→ **撞索引，第二次删除直接报错**。

本项目方案：
1. 唯一索引降级为普通索引（V4 迁移）
2. 唯一性由应用层校验，只查"未删除"范围
3. 软删除时改写唯一码为 `原码__del_时间戳`，立即释放原编码
4. 全局异常处理器捕获并发场景下的唯一索引冲突，翻译为友好提示

**Q：迁移脚本里为什么用子查询而不是硬编码部门 ID？**

硬编码 ID 在 ID 因测试数据漂移后会触发外键失败（我实际遇到了 Error 1452）。
子查询按业务编码关联，脚本在任何库上都能执行：

```sql
department_id = (SELECT id FROM sys_department WHERE code = 'IT_DEV')
```

**Q：为什么用原生 SQL 而不是 JPQL？**

JPQL 的 `LEFT JOIN ... ON` 是 Hibernate 的扩展语法，不是 JPA 标准。
换用其他 JPA 实现（如 EclipseLink）会直接报错。
原生 SQL 在任何 JPA 实现下行为都一致，代价是失去数据库可移植性——
但本项目只支持 MySQL，这个代价可以接受。

## 关于性能

**Q：怎么保证用户列表不产生 N+1 查询？**

部门名称需要随用户列表返回。直接实现是循环里逐个查部门，返回 N 个用户就是 N+1 次查询。

实现是**单条联表 SQL** 取「用户ID → 部门名」映射，在内存中组装 DTO：
```sql
SELECT a.id, d.name FROM sys_account a
JOIN sys_department d ON a.department_id = d.id
WHERE a.deleted = ? AND a.department_id IS NOT NULL
```

整个接口固定 2 条 SQL，与数据量无关。
分页接口进一步收窄为 `WHERE a.id IN (:ids)`，只处理当前页数据。

**Q：三个筛选条件为什么用 Specification 而不写派生查询？**

三个条件（username / status / roleLevel）组合是 2³ = 8 种。
派生方法要写 8 个 `findBy...`，条件一多就是方法爆炸。

Specification 用代码拼 Predicate 数组，条件为 null 就跳过，
以后加"按部门筛选"只需增加几行，不用新增方法。

**Q：分页接口做了哪些边界防护？**

需求没要求，但我加了：
- `page < 0` → 兜底 0（否则 `PageRequest.of` 抛异常）
- `size <= 0` → 兜底 1
- `size > 100` → 限制 100，**防止一次请求拉取全表**
- 翻页超出总页 → 返回空列表而非报错
- 前端：删完当前页最后一条自动回退一页，避免停留在空白页

## 关于工程实践

**Q：数据库为什么不用 root 连接？**

root 是超级管理员，拥有 `*.*` 权限，能执行 `DROP DATABASE`。
如果应用有 SQL 注入或程序 bug，用 root 连接意味着**整个实例的数据都可能丢失**。

业务账号只授权单个库：
```sql
GRANT ALL PRIVILEGES ON `xt_interview`.* TO 'admin'@'localhost';
```
`xt_interview.*` 是"该库下所有表"，与 `*.*`（所有库所有表）是不同层级。

即使出现安全漏洞，影响范围也被限制在单个业务库内。这是最小权限原则。

**Q：MySQL 的账号是库级还是实例级？**

**实例级**。账号 `admin@localhost` 挂在整个 MySQL 实例上，密码全局唯一一份，
不会因为访问的库不同而不同。

会出现"感觉不一样"的情况有几种：
- 同一用户名在不同实例（本地 vs 远程）密码不同
- `localhost` 与 `127.0.0.1` 在权限系统里是两个主体，需分别授权
  （实测本机因反向解析，`127.0.0.1` 连接仍命中 `admin@localhost`，只需授权一个）

**Q：为什么密码存在配置文件里？**

改成了环境变量外置：
```properties
spring.datasource.password=${DB_PASSWORD:123456}
```
冒号后是默认值，本地开箱即用；部署时通过环境变量注入真实凭据，无需改代码。

同时把数据库密码与 JWT 密钥都从代码中移除了硬编码值。

**Q：MD5 存密码安全吗？**

不安全。MD5 是单向哈希但没有加盐，且计算极快，可被彩虹表和暴力破解。

生产环境应该用 BCrypt（自带随机盐、计算慢）。
我在 `SecurityConfig` 中已经提供了 `PasswordEncoder` Bean，但没有启用切换——
因为存量数据是 MD5，直接切换会导致历史账号无法登录。
这是"技术债"的典型处理方式：把正确的方案准备好，但要选时机切换。

## 关于取舍与不足

**Q：这个项目还有哪些不足？**

坦率地说有五点：

1. **密码用 MD5** —— 存量兼容问题，方案已备好待切换
2. **无刷新令牌** —— JWT 有效期 24 小时，过期需重新登录
3. **部门无层级** —— 当前是平铺结构 + 编码语义分组，未建 parent_id 树形关系
4. **无自动化测试** —— 功能验证依赖 curl 实测，没写单元测试和集成测试
5. **软删除数据无清理机制** —— 历史记录无限累积，需要定期归档

第 4 点是我认为最该补的。生产级项目应该有测试覆盖，
尤其 `PermissionChecker` 这种权限核心逻辑，应该有完整的单元测试矩阵。

**Q：如果给你更多时间，你会优先做什么？**

优先级排序：
1. **补单元测试** —— 尤其是权限模块，越权逻辑必须被测试锁死
2. **部门层级** —— 加 parent_id，支持树形展示，企业真实需求
3. **审计日志** —— 谁在什么时候改了谁，这个审计字段目前是缺失的

## 可能被问到但项目里没做的

**Q：为什么没有用 Redis 做缓存？**

当前数据量（50 个账号）不需要缓存，加了反而增加运维复杂度。
但 JWT 权限校验每次回库是明确的扩展点 —— 高并发下应该把权限放入 Redis，
管理员变更权限时主动失效缓存。

**Q：怎么防止 CSRF？**

项目是纯 token 鉴权的 REST API，token 存在 localStorage 并通过 Authorization 头发送，
不使用 Cookie 会话，所以 CSRF 不适用。`SecurityConfig` 中已显式关闭。

**Q：token 存在 localStorage 安全吗？**

存在 XSS 风险（若页面被注入恶意脚本可读取 token）。
更安全的方案是 httpOnly Cookie + 刷新令牌，或改用内存 + 短期访问令牌。

骨架用的是 localStorage，我没有改动是因为这超出了任务范围。
但要真正做企业级认证，这一定是第一个要改的地方。
