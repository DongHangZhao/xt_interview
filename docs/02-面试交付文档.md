## 一、项目概述

基于 Spring Boot 4 + Vue 3 的用户/部门管理系统。在原始骨架的基础上完成了三项开发任务，
并针对骨架中发现的三个安全隐患做了生产级修复。

| 项目 | 内容 |
|------|------|
| 后端 | Spring Boot 4.0.6 / Java 21 / Spring Data JPA / Flyway / Spring Security / JWT |
| 前端 | Vue 3.4 / Vite 5 / TypeScript / Element Plus / Pinia / Vue Router |
| 数据库 | MySQL 8.0，Flyway 版本化迁移 |
| 数据规模 | 21 个部门 / 50 个账号 |

**原项目骨架已完成的功能**：JWT 登录、用户管理 CRUD、侧边栏导航。
**本次新增**：部门管理、用户-部门关联、搜索分页（选做）、RBAC 权限体系。

## 四、超出基础要求的设计

以下四项不在原始需求文档中，是开发过程中发现问题后主动补充的。

### 4.1 修复骨架中的越权漏洞（安全性）

**问题**：骨架中 `role_level` 字段从未被任何代码用于鉴权。
JWT payload 携带 `roleLevel`、`JwtAuthenticationFilter` 将其写入 request attribute，
但后续无任何读取与判断。实测任意登录用户均可创建管理员、删除任意账号。

**修复**：新增完整 RBAC 体系，核心逻辑集中在 `PermissionChecker`：

```
普通用户(1)  只能查看/修改自己，无任何管理权限
管理员(2)    可管理用户与部门，不能创建同级及以上、不能操作同级及以上、不能操作自己
超管(3)      可管理全部账号与部门（含创建同级超管），唯一仍禁止操作自己
```

四处关键设计：

1. **不信任 JWT 中的权限声明**
   JWT 签发后至过期前（24 小时），用户权限可能被管理员调整，或账号被禁用。
   若直接使用 token 内的旧 `roleLevel` 判权，权限下调后旧 token 仍持有高权限。
   → `JwtAuthenticationFilter` 每次请求按主键回查实时权限，同时校验账号是否被禁用/软删除。
   成本为一次主键索引查询，可接受。

2. **ThreadLocal 必须 finally 清理**
   Tomcat 采用线程池复用线程。若不清理，下一个请求可能读到上一个用户的权限对象，
   构成隐蔽且严重的越权。
   ```java
   try { filterChain.doFilter(request, response); }
   finally { UserContext.clear(); }
   ```

3. **"修改我的资料"采用字段白名单**
   该接口只处理 `name / phone / gender / username / newPassword` 五个字段，
   **完全不读取** `roleLevel / isSuper / status / departmentId`。
   即使前端恶意提交这些字段也不会落库，从根上杜绝自我提权。
   接口不接收 id 参数，后端从 token 识别当前用户，物理上无法修改他人。

4. **同级保护使用 `>=` 而非 `>`**
   最初的实现允许管理员创建同级管理员，却禁止修改同级，逻辑不自洽；
   且两个管理员可通过配合将第三个管理员提升为超管（横向提权）。
   → 统一为 `target >= operator.getRoleLevel()` 拦截，超管单独放行。

实测结果：

| 身份 | 操作 | 结果 |
|------|------|------|
| 普通用户 | 创建管理员 / 查看他人 / 创建部门 | 403 |
| 普通用户 | 提交 `roleLevel:3` 到 my-profile | 200，但字段被忽略，库中仍为 1 |
| 管理员 | 创建超管 / 创建同级 / 设 isSuper / 改超管 / 删自己 | 403 |
| 超管 | 创建超管 / 修改他人 | 放行 |
| 超管 | 修改自己 | 403 |
| 禁用账号 | 登录 | 403 |

### 4.2 软删除与唯一索引的正确处理

**问题**：唯一索引作用于物理行，软删除仅标记 `deleted=1`，行仍在库中且仍占用索引。
若应用层只校验"未删除范围内唯一"，会出现「校验通过但插入被唯一索引拦截」→ HTTP 500。

本项目采取的方案：

1. **唯一性下移至应用层**：V4 迁移将 `uk_department_code` / `uk_username`
   降级为普通索引（保留查询性能），唯一性由 Service 层校验。
2. **软删除时改写唯一码**：`test` → `test__del_1789012345678`。
   保留审计记录的同时立即释放原编码。
3. **并发兜底**：`GlobalExceptionHandler` 捕获 `DataIntegrityViolationException`
   并翻译为可读提示，避免任何路径漏出 500。

> 明确否决了 `UNIQUE(code, deleted)` 方案：连续删除两个同 code 记录时，
> 两行均为 `(code, 1)` 会再次撞索引，属于定时炸弹。

### 4.3 N+1 查询规避

部门名称需随用户列表返回。直接实现会是 N+1（返回 N 个用户 = N+1 次查询），
用户量增长后接口显著变慢。

实现：单条联表 SQL 取出「用户ID → 部门名」映射，在内存中组装 DTO。
- 列表接口：一次全表联表
- 分页接口：`WHERE a.id IN (:ids)`，仅处理当前页数据

整个接口固定 2 条 SQL，与数据量无关。

> 补充：使用**原生 SQL** 而非 JPQL，因 JPQL 的 `LEFT JOIN ... ON` 属 Hibernate 扩展语法，
> 换用其他 JPA 实现会失效。

### 4.4 统一异常体系

骨架中 Service 层直接抛 `RuntimeException`，项目无全局异常处理器，
Spring 返回 HTML 错误页，前端 axios 读不到 `message` 字段，
导致「部门编码已存在」这类校验信息完全无法呈现。

补充 `BusinessException`（业务异常 → 400）+ `@RestControllerAdvice`（兜底 → 500），
统一收敛为 `{ success, message }`，与前端拦截器约定一致。

## 五、数据库设计

### 迁移脚本

| 版本 | 说明 |
|------|------|
| V1 | 建 `sys_account` 表 + admin 种子数据 |
| V2 | 建 `sys_department` 表 + 研发部/运维部种子数据 |
| V3 | `sys_account` 加 `department_id`，建外键与索引 |
| V4 | 唯一索引降级为普通索引 |
| V5 | 企业级演示数据（18 部门 + 48 账号） |

### 关键约束

```sql
-- 外键：部门删除时置空而非级联，避免连带删除用户
CONSTRAINT fk_account_department
    FOREIGN KEY (department_id) REFERENCES sys_department(id)
    ON DELETE SET NULL ON UPDATE CASCADE
```

`ON DELETE SET NULL` 的选择理由：部门采用软删除，若为 `CASCADE` 或 `RESTRICT`，
物理删除部门会导致用户记录丢失或操作被阻断，与"部门为可选字段"的业务定位冲突。

### V5 的一个细节

部门 ID 一律使用子查询而非硬编码：

```sql
department_id = (SELECT id FROM sys_department WHERE code = 'IT_DEV')
```

硬编码 ID 在部门 ID 因测试数据发生漂移后会触发外键失败（MySQL Error 1452），
且换库执行同样失败。此写法在任何库上均可执行。

## 六、技术决策记录

### 6.1 Spring Boot 4 的接口变更

Spring Data JPA 4 起，`Specification` 动态查询不再混入 `JpaRepository`，
必须显式继承 `JpaSpecificationExecutor`：

```java
public interface AccountRepository
    extends JpaRepository<Account, Long>, JpaSpecificationExecutor<Account> {}
```

否则 `findAll(spec, pageable)` 编译报错。
Boot 2.x / 3.x 的社区资料均不适用。

### 6.2 为何用 Specification 而非派生查询

筛选条件为 username / status / roleLevel 三项，组合数为 2³ = 8 种。
使用 Spring Data 派生方法需编写 8 个方法，随条件增加呈指数爆炸。
Specification 通过代码拼接 Predicate，未填写的条件自动跳过，后续扩展仅需增加几行。

### 6.3 Spring Security 的接入方式

引入 `spring-boot-starter-security`，但 `SecurityFilterChain` 采用**放行**策略：

```java
.anyRequest().permitAll()
```

原因是本项目的认证链路已由自建 `JwtAuthenticationFilter` → `UserContext`
→ `PermissionChecker` 完整承担。若再让 Spring Security 接管认证，
会出现两层过滤器同时鉴权、规则重复且难以定位的问题。

保留 `@EnableMethodSecurity` 使 `@PreAuthorize` 可用，便于后续细化。
关闭 CSRF（纯 token REST API，无 Cookie 会话）、formLogin、httpBasic。

### 6.4 前端页码基数转换

后端 `page` 按需求从 0 开始，Element Plus `el-pagination` 从 1 开始。
最初使用 `v-model:current-page="query.page"` 会因双向绑定把 1-based 值
直接写回 0-based 变量导致翻页错乱。
→ 改为单向绑定 `:current-page="query.page + 1"`，在 `@current-change` 中做 `val - 1`。

### 6.5 前端类型问题修复

骨架 `UserManagement.vue` 存在两个 TypeScript 错误：

```
TS2740: AxiosResponse 赋给 any[] 缺 length/push...
TS2790: delete 的操作数必须是可选属性
```

根因：响应拦截器剥离了 `response.data`，但 axios 的类型签名仍标注 `AxiosResponse<T>`，
属"运行时行为与类型声明不一致"。

修复：在 `request.ts` 导出泛型化的 `get/post/put/del`，显式声明 `Promise<T>`；
`delete` 非法通过 `Record<string, any>` 让字段变为可选解决。

**修复后 `npx vue-tsc --noEmit` 零报错。**

### 6.6 数据库账号权限

```sql
GRANT ALL PRIVILEGES ON `xt_interview`.* TO 'admin'@'localhost';
```

`xt_interview.*` 指该库下所有表，与 root 的 `*.*`（所有库所有表）是不同层级。
不使用 root 连接业务应用是最小权限原则的实践：即便出现 SQL 注入或程序 bug，
影响范围也被限制在单个业务库内。

### 6.7 配置外置

```properties
spring.datasource.username=${DB_USERNAME:admin}
spring.datasource.password=${DB_PASSWORD:123456}
```

冒号后为默认值，本地开箱即用；部署时通过环境变量注入真实凭据，无需修改代码。

## 八、已知限制

1. **密码使用 MD5**。骨架沿用的 MD5 不具备抗碰撞性，生产环境应使用 BCrypt。
   已在 `SecurityConfig` 中提供 `PasswordEncoder` Bean，但未启用切换，
   因存量数据为 MD5，直接切换会导致历史账号无法登录。
2. **无刷新令牌**。JWT 有效期 24 小时，过期需重新登录。
3. **未实现部门层级**。当前部门为平铺结构 + 编码语义分组，未建 parent_id 树形关系。
4. **无自动化测试**。功能验证依赖 curl 实测，未编写单元测试与集成测试。
5. **软删除数据无清理机制**。历史记录无限累积，需定期归档。

## 十、目录结构

```
src/main/java/com/xt/interview/
├── config/          SecurityConfig（权限配置）、WebMvcConfig（跨域）
├── controller/      接口层，只做参数接收与响应封装
├── service/         业务层，承载业务规则与权限校验
│   └── impl/
├── repository/      数据层，含联表查询与 Specification
├── entity/          数据库表映射
├── dto/             前后端数据传输对象
├── security/        PermissionChecker（权限核心）、UserContext、LoginUser
├── exception/       BusinessException、GlobalExceptionHandler
├── enums/           RoleLevel
└── util/            JwtUtil、MD5Util、SoftDeleteCodeUtil

frontend/web/src/
├── api/             接口请求封装 + TypeScript 类型定义
├── router/          路由 + 管理员权限守卫
├── stores/          Pinia 登录状态与权限计算
├── utils/           axios 封装（token 注入、错误拦截）
├── layouts/         侧边栏与顶栏
└── views/           Login / UserManagement / DepartmentManagement / Profile
```

分层约束：Controller 不含业务逻辑；Service 不依赖 HTTP 类型；
权限判定统一收敛在 `PermissionChecker`，不在 Controller 散落。
